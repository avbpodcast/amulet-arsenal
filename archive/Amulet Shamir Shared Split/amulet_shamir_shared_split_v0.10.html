Recommended: tap the dice button (or the link below the meter) and let the vault roll a passphrase for you. Six random words gives ~77 bits of entropy, eight gives ~103, both well above the 70-bit floor where offline attacks become a concern. Random words beat clever short strings on every axis: stronger, easier to write on paper, easier to type back later.
How does this work?
The dice button picks words at random from the EFF Large Diceware list: a hand-curated set of 7,776 short, easy-to-spell English words. Spaces between the words are fine and recommended — they make the passphrase easier to read and type.
How the bits add up. Diceware entropy is log₂(wordlist_size) × number_of_words. With 7,776 words, that is log₂(7,776) ≈ 12.92 bits per word.
  • 6 random words: 12.92 × 6 ≈ 77.5 bits
  • 8 random words: 12.92 × 8 ≈ 103.4 bits
  • 10 random words: 12.92 × 10 ≈ 129 bits
Letters inside each word are not independent random characters — once a word is picked, every letter in it is determined. So you don't get character-level entropy on top of the word entropy. The numbers above are the real ceiling for a Diceware passphrase of this length.
The strength meter below estimates your entropy in real time and flags common patterns (keyboard runs, common words, digit sequences). Want extra safety? Use 8 or more words.
What protects the vault behind the password?
Your vault uses Argon2id for maximum protection against brute-force attacks. The unlock time is tuned for security and convenience: about 0.5 to 1 second on typical user hardware, longer on older machines. Argon2id is memory-hard and GPU-resistant, so an attacker who steals the encrypted vault file still has to spend real money on every guess they try. With a 70-bit-or-stronger passphrase plus this KDF, offline cracking stays impractical on civilian hardware budgets for years. The exact parameters (m=32 MiB, t=2, p=1) sit above the current OWASP minimum and are saved alongside each encrypted file so you can change defaults later without breaking older vaults.

If you type your own password, it must have:
Diceware passphrase recognised. Every word is in the EFF Large list, so the letter / number / special character rules below are skipped automatically.
  • 10 or more characters in total
  • at least one letter (a-z or A-Z)
  • at least one number (0-9)
  • at least one special character (e.g. ! @ # $ % ^ & * ( ) [ ] { } + - = _ | \ / ~ < > , . ? : ; ' " €)
  • 77 or more bits of entropy (the meter above)
Generator-rolled passphrases skip the letter / number / special requirements: 8 random words from the EFF list already give ~103 bits, which is well above the floor and is easier to write down than a string with punctuation.
Write the passphrase shown above down before you continue. It is the only way to unlock the vault: lose it and the vault is permanently inaccessible. About 103 bits of entropy (8 random words × log₂(7,776) ≈ 12.92 bits each, from the EFF Large Diceware list).

Forget vault?

This wipes everything this browser tab currently holds about your vault. It's stronger than Lock (which keeps the encrypted files around for a quick re-unlock) — after Forget, nothing decrypted remains in this tab and, if applicable, the on-disk vault files are erased too.

What gets wiped:
  • Every decrypted wallet and timelock payload held in memory.
  • Every password field, mnemonic, private key, and note currently visible on screen.
  • The system clipboard (best-effort — clipboard-manager history is outside our reach).
  • Local browser storage used by the vault (just the theme setting).
  • If you opened a vault folder directly: vault.meta and every .enc in that folder are overwritten with zeros and unlinked.
What this does NOT touch:
  • Your downloaded .zip backup — the vault has no way to reach it from here. If you want it gone, delete it with your OS file manager.
  • OS swap / hibernation files — if the kernel paged out memory containing a seed during this session, that swap page isn't something a browser script can scrub. Close the browser and reboot for full session hygiene.
  • Browser / SSD internal caches — V8 heap pools, SSD over-provisioned cells, and clipboard-manager histories all sit outside the JS sandbox.

How to verify file integrity

Compare the SHA‑256 of this HTML file against the canonical hash published by the project author. Matching = nobody has modified the file since release. Not matching = stop using this file.

Why can't the page hash itself automatically?
Browsers block pages opened from file:// URLs from reading their own source via fetch() — a security measure that also blocks self-verification. When you drop the HTML file onto the panel, the browser reads it via the standard file-picker API and we compute SHA‑256 in-memory. No network, no file write.
Computed hash (after you've dropped the file)
—
Alternative: compute the hash yourself from the command line
Linux / macOS: sha256sum amulet_vault.html macOS (BSD): shasum -a 256 amulet_vault.html Windows (PS): Get-FileHash amulet_vault.html -Algorithm SHA256
Honest limitation: by the time you see this hash, the page has already loaded and any code in the file has already run. The check is a detection tool, not a defense. For a file you don't trust at all, compute the hash on the command line before opening it in a browser. A hash computed inside the page can be faked by a sufficiently tampered file — the command-line check cannot.
